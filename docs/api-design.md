# GrievX API Design

## 1. API conventions

- Base path: `/api/v1`; JSON responses use ISO-8601 UTC timestamps and UUIDs.
- Authentication: `Authorization: Bearer <access-token>`.
- Student complaint endpoints return only the authenticated student's records.
- OpenAPI generated by FastAPI is the authoritative machine-readable contract.

## 2. Endpoint groups

| Group | Routes | Authorization |
| --- | --- | --- |
| Health | `GET /health/live`, `GET /health/ready` | public/internal deployment policy |
| Auth | `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me` | anonymous/authenticated as applicable |
| Access | role-specific protected dashboard routes | role-scoped |
| Complaints | `POST /complaints`, `GET /complaints`, `GET /complaints/{id}` | authenticated students; own records only |

## 3. Week 4 complaint contract

### Create complaint

`POST /api/v1/complaints` uses `multipart/form-data`:

- `description`: required, trimmed, 10-5000 characters.
- `latitude`: required, -90 to 90.
- `longitude`: required, -180 to 180.
- `location_label`: optional, maximum 255 characters.
- `image`: optional JPEG, PNG, or WebP evidence image.

The API requires a valid student JWT. A successful request returns `201 Created`, a generated `GRV-...` complaint ID, `SUBMITTED` status, location, evidence metadata, and initial status history.

Images are stored in MinIO using generated object keys. The original filename is retained only as metadata; object keys are never derived solely from user-provided filenames.

### List complaints

`GET /api/v1/complaints` returns the authenticated student's complaint history. Other students cannot see these records.

### Complaint detail

`GET /api/v1/complaints/{id}` returns the authenticated student's complaint, evidence metadata, current status, and status history. A complaint belonging to another student is returned as `404 Not Found` to avoid exposing its existence.

### Validation and storage

- Authentication and role checks happen in the backend; mobile route visibility is not a security boundary.
- Image MIME type is allow-listed and the file signature is verified with Pillow.
- Image size is bounded by `MAX_COMPLAINT_IMAGE_SIZE_BYTES` (10 MiB by default).
- Invalid coordinates are rejected.
- If object storage succeeds but the database transaction fails, the uploaded object is removed to avoid an orphaned evidence object.
- No AI analysis, classification, prioritization, routing, or automated inference runs in Week 4.

## 4. Future endpoint groups

Lifecycle, assignment, AI review, incidents, notifications, analytics, map, model governance, and audit endpoints remain later-week work.


## 5. Week 5 admin complaint management

The Week 5 operations API is under `/api/v1/admin` and is protected by backend RBAC.

| Route | Purpose | Authorization |
| --- | --- | --- |
| `GET /admin/overview` | Dashboard counts by lifecycle status | Admin, Staff, Department Head |
| `GET /admin/complaints` | Searchable/sortable complaint queue | Admin, Staff, Department Head |
| `GET /admin/complaints/{id}` | Permission-scoped complaint detail | Admin, Staff, Department Head |
| `GET /admin/complaints/{id}/images/{image_id}` | Short-lived evidence-image URL | Admin, Staff, Department Head |
| `GET /admin/complaints/departments` | Departments available to the operator | Role-scoped |
| `GET /admin/complaints/staff` | Active staff available for assignment | Role-scoped |
| `PATCH /admin/complaints/{id}/assignment` | Assign/reassign department and staff | Admin only |
| `PATCH /admin/complaints/{id}/priority` | Manually change priority | Admin, Staff, Department Head within scope |
| `PATCH /admin/complaints/{id}/status` | Change lifecycle status | Admin, Staff, Department Head within scope |

Supported query parameters for the queue are `q`, `status`, `priority`, `department_id`, `assigned_staff_id`, `sort`, and `order`.

### Week 5 lifecycle rules

Valid transitions are:

```text
SUBMITTED   -> ASSIGNED, REJECTED
ASSIGNED    -> IN_PROGRESS, REJECTED
IN_PROGRESS -> RESOLVED, REJECTED
RESOLVED    -> CLOSED, IN_PROGRESS
CLOSED      -> terminal
REJECTED    -> terminal
```

Invalid transitions return `409 Conflict`. Successful changes append `complaint_status_history` and create an administrative audit record.

### Access scope

- **Admin:** campus-wide complaint visibility and assignment controls.
- **Department Head:** complaints in their department.
- **Staff:** complaints in their department or explicitly assigned to them.
- **Student:** denied access to the admin complaint-management routes.

Reporter information is limited to non-secret identity fields. Password hashes and access tokens are never returned.


## 6. Week 6 complaint lifecycle and notifications

The complaint lifecycle is recorded in complaint_status_history for every successful state change:

SUBMITTED -> ASSIGNED -> IN_PROGRESS -> RESOLVED -> CLOSED

The existing REJECTED terminal path from Week 5 remains supported for administrative rejection.

| Route | Purpose | Authorization |
| --- | --- | --- |
| GET /notifications | List the authenticated user's in-app notifications and unread count | Authenticated user |
| PATCH /notifications/{id}/read | Mark an owned notification as read | Notification owner |
| WS /ws/notifications?token=<JWT> | Receive realtime notification events | Authenticated user |

Notification event types are COMPLAINT_SUBMITTED, DEPARTMENT_ASSIGNED, STAFF_ASSIGNED, STATUS_CHANGED, and COMPLAINT_RESOLVED.

Recipients are scoped to the complaint stakeholders: the reporting student, assigned staff, department heads for the complaint department, and active admins. The database notification row is created in the same transaction as the lifecycle change. After commit, connected WebSocket clients receive the same event payload.

The WebSocket implementation is intentionally WebSocket-first and keeps the client contract independent from transport internals. The current connection manager is in-process; Redis fan-out can be added for multi-instance deployment without changing the mobile/admin event contract.

The student mobile app displays current status, an append-only timeline, and an in-app notifications tab. The operations dashboard refreshes immediately on realtime events and also uses a 15-second fallback refresh.
