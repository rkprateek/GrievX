# GrievX API Design

## 1. API conventions

- Base path: `/api/v1`; JSON responses use ISO-8601 UTC timestamps and UUIDs.
- Authentication: `Authorization: Bearer <access-token>`. Refresh tokens are rotated using a secure, documented client-specific flow.
- Pagination: `limit` (default and maximum documented) and opaque `cursor`; never return an unbounded complaint queue.
- Errors: RFC 9457-style problem payload with `type`, `title`, `status`, `detail`, `instance`, and a safe request ID.
- Write requests support `Idempotency-Key` where client retry could create duplicate complaint, notification, or lifecycle actions.
- OpenAPI generated by FastAPI is the authoritative machine-readable contract; examples below are architectural, not implemented Week 1 endpoints.

## 2. Endpoint groups

| Group | Routes | Authorization |
| --- | --- | --- |
| Health | `GET /health/live`, `GET /health/ready` | public/internal deployment policy |
| Auth | `POST /auth/login`, `/auth/refresh`, `/auth/logout`, `GET /auth/me`, password reset flow | anonymous/authenticated as applicable |
| Users and roles | `GET/PATCH /users/{id}`, `GET/POST/PATCH /users`, `GET/POST /roles`, `PUT /users/{id}/roles` | self or Super Admin by action |
| Departments | `GET/POST /departments`, `GET/PATCH /departments/{id}`, memberships | read by operations users; admin governance writes |
| Locations | `GET /locations`, `GET/POST/PATCH /locations/{id}` | students read active locations; admin manages |
| Complaints | `POST /complaints`, `GET /complaints`, `GET/PATCH /complaints/{id}`, `POST /complaints/{id}/images`, `GET /complaints/{id}/history` | student owns own records; operations roles scoped/privileged |
| Lifecycle and assignment | `POST /complaints/{id}/transitions`, `POST /complaints/{id}/assignments`, `DELETE /complaints/{id}/assignments/{assignmentId}` | staff/heads/admin according to transition and scope |
| AI review | `GET /complaints/{id}/predictions`, `POST /complaints/{id}/predictions/{predictionId}/review`, `POST /complaints/{id}/analysis` | operations review; server/worker analysis trigger policy |
| Incidents | `GET/POST /incidents`, `GET/PATCH /incidents/{id}`, `POST /incidents/{id}/complaints`, `DELETE /incidents/{id}/complaints/{complaintId}` | department head/admin based on scope |
| Notifications | `GET /notifications`, `POST /notifications/{id}/read`, preferences | user owns own notifications |
| Analytics and map | `GET /analytics/overview`, `/analytics/departments`, `/map/complaints`, `/map/incidents` | department-scoped or admin aggregate access |
| Models and audit | `GET /model-versions`, `POST /model-versions/{id}/activate`, `GET /audit-logs` | Super Admin; audit read may be separately delegated |

## 3. Key resource contracts

### Create complaint

`POST /api/v1/complaints` accepts a title, description, selected `location_id` or validated coordinates, optional client request ID, and evidence upload references. It returns `201 Created` with the server reference number, `submitted` status, and an analysis state; it does not wait for costly ML inference.

### Media flow

1. Client requests authorized upload intent: `POST /complaints/{id}/images/upload-intents`.
2. API validates permission, count, MIME allow-list, size and creates a short-lived object-store upload URL.
3. Client uploads directly to object storage.
4. Client completes registration: `POST /complaints/{id}/images/{imageId}/complete`.
5. Worker scans/processes the object; API exposes only `ready` evidence to authorized readers.

### Status transition

`POST /complaints/{id}/transitions` accepts `{ "to_status": "in_progress", "reason": "Technician dispatched", "version": 3 }`. The service validates caller scope, allowed transition, current version, and assignment rules; it atomically updates complaint state, adds status history, emits an audit event, and queues notifications.

### Prediction review

`POST /complaints/{id}/predictions/{predictionId}/review` accepts `{ "decision": "override", "value": "high", "reason": "Exposed live wiring visible" }`. Review does not mutate historical model output; it adds reviewer data to the prediction and applies the authorized operational value separately.

## 4. Authorization matrix

| Resource/action | Student | Staff | Dept Head | Admin | Super Admin |
| --- | --- | --- | --- | --- | --- |
| Own complaint create/read | Yes | N/A | N/A | Yes | Yes |
| Department queue/read evidence | No | Assigned/scoped | Department | All | All |
| Assign staff | No | No | Own department | All | All |
| Reassign department | No | No | Request only | Yes | Yes |
| Resolve assigned complaint | No | Assigned only | Department | All | All |
| Manage roles/model activation | No | No | No | No | Yes |

All matrix decisions are enforced in FastAPI policies and tested at the API level; frontend route guards only improve usability.
